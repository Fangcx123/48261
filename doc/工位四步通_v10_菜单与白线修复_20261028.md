# v10 菜单参数与后台图像白线修复

日期：2026-10-28。工程仍为 `src/td_project_workstation_v10/HDMI1.4b_Transmitter_v1.0.al`。

> 后续：v11 已定位白线及多分辨率读图乱码的根因（SDRAM 读数据比读有效早一个周期），见 [v11 读图乱码修复](工位四步通_v11_读图乱码修复_20261029.md)。

## 反馈与定位

板上反馈：参数菜单右侧出现“系系系”；PIC2–PIC4 有持续存在、位置基本固定的白线。

菜单问题已通过 Tang Dynasty RTL 优化后网表复现：原本选择数字/空白和文字 ROM 的混合路径，在 ROM 提取后丢失了选择逻辑，数字位置读到文字地址 0 的“系”。现统一使用同步文字 ROM，增加空白及 0–9 的地址，避免该混合路径。修复后的优化网表与 RTL 对四帧全部像素一致，包含百分比、静音、轮播秒数、语音状态和普通画面旁路。

图像通路发现读写交接缺口：原 `frame_fifo_write` 不使用已有的控制器 busy/refresh 输入，突发应用写结束后很快释放总线，而控制器内部写入仍可能在收尾。首图提前显示后，后台写图与持续读图并行，会反复经过这个边界。修复在启动整笔写事务前检查控制器状态，突发中保持连续，结束后保持写占用至少 16 个内存周期，并继续等待 busy/refresh 解除；显示读事务启动也检查控制器 busy/refresh。16 周期防护与原缩略图写入收尾策略一致。

这属于已验证的接口时序缺口修正；尚未在真实开发板复现并消除白线，因此不能将其写成已经上板证实的唯一根因。

## 验证范围

- `menu_after_compare.log`：厂商 RTL 优化后网表与参考 RTL 四帧逐像素一致。不是最终带布线延迟的时序仿真。
- `write_handoff_before.log` / `write_drain_before.log`：旧代码的预期失败，分别暴露忙期间发起写入、收尾前释放占用；不作为通过记录。
- `write_handoff_fix.log`：新代码在控制器忙/刷新、突发中途忙/刷新、16 周期收尾情况下通过，256 个字地址和上下翻转正确，两个 128 字突发不中断。
- `background_integrity_fix.log`：真实异步 FIFO、100 MHz 源/41.667 MHz 内存/25 MHz 像素时钟；持续显示期间写入整张后台图、生成整帧四图预览。检查每个后台写地址和像素，以及冲突、溢出、显示下溢。
- `fourbank_fix.log`：四银行数据通路、连续视频与帧提交。
- `video_fix.log` / `control_fix.log` / `scaler_fix.log` / `syntax_fix.log`：菜单/字幕/预览、按键/调度、背压下 320×240 与 1920×1080 全帧像素、顶层语法。

后台与四银行仿真使用行为级内存；厂商控制器及物理 SDRAM 加密模型未进行完整功能仿真，不能替代板上验收。对不完整的控制器导出网表所做探索不纳入有效验证。

菜单数字译码另外按有限的百分比档位和 6 位秒数收窄，消除通用除法/取余的资源消耗。字形 ROM 使用固定 1024×16 深度、6 位字形索引及无复位的同步读端口，使厂商工具将字库实现为片上 BRAM。单独综合菜单模块的 LUT 等效用量由约 1148 降至 647，BRAM 用量为 3。`menu_decoder_equivalence.log` 对比修改前 RTL 四帧全部像素，`menu_digits_fix.log` 覆盖全部 256 个百分比输入和 64 个秒数值。首次打包超出 48 个 MSLICE，单独优化数字译码仍不足，因此增加了字库 BRAM 调整；失败日志已单独保存，不纳入通过记录。

### TD 界面重新编译的配置补充

第二次 GUI 失败日志 `gui_phy_failure_second_20261028.log` 仍是同一个资源冲突，且当时 `.al` 与本次运行 `.prj` 都没有 seed 设置。后台进程保存工程不能更新已打开 GUI 的内存配置。应在用户正在使用的 TD 窗口下方 **Tcl Console** 中执行 `source D:/FPGA/lab_ex5_i2s/verification/workstation_v10/configure_current_td_window.tcl`，确认设置命令没有报错后，再通过界面重新运行 Phy Opt。该脚本只设置参数，不重置或启动编译，也不烧录。直接重新综合会重置实现状态，因此要在重新综合完成后核对参数，再运行 Phy Opt。

本次已运行完整 `rebuild_display_fix.ps1`，从清空综合结果开始重新综合、布局布线、生成 bit、保持修正、重新生成交付 bit 和发布校验全部通过；见 `full_rebuild_gui_fix.log` 与 `build_display_fix.log`。最终仍为 SWNS +0.110 ns、HWNS +0.024 ns。该结果验证的是命令行完整流程，尚未直接操作用户当前 GUI 窗口。

用户随后在 TD 界面重编译时再次出现 `PHY-8023`（`x27y24_e2beg3` 布线冲突）和 `RUN-8102`。检查发现磁盘工程的物理实现策略没有保存布局种子，而独立重建脚本中已指定种子 1。现已通过工具将 `PlaceProperty/seed=1` 写入 v10 `.al` 工程，并用独立进程重新打开确认。当前打开的旧 TD 窗口仍可能持有默认配置；应关闭工程且不保存旧配置，再重新打开磁盘上的 v10 工程。也可在当前窗口 Tcl 控制台先执行 `set_param place seed 1 -run phy_1`，使窗口内配置一致，再保存。

完整重建仍建议使用 `verification/workstation_v10/rebuild_display_fix.ps1`，它包含保持时间修正和最终 bit 校验。脚本现同时检查 syn_1/phy_1 子流程日志，避免只检查主进程返回码而漏掉实现错误。功能 RTL 与本次发布的 80 个源码/约束摘要保持一致。

保存配置后的独立重开验证已通过：`verify_saved_seed.log` 读取到 `place::seed::1`，未临时设置种子即完成 `Run phy_1 success` 和 bitgen。随后重新执行保持修正，最终 SWNS +0.110 ns、HWNS +0.024 ns。原发布 bit 与清单已备份为 `display_fix_before_seed_rebuild.bit` 和 `display_fix_before_seed_rebuild_manifest.json`。

最终构建已完成。默认布局种子的一次布线存在资源冲突，改用 `place seed 1` 后通过布线并生成 bit；重建入口已固定该参数。记录见 `retry_display_route.log`，默认种子失败记录单独保留在 `display_fix_route_fail_phy.log`。随后执行 `fix_hold -eco` 修复六处短路径保持违例，并从修复后的数据库重新生成交付 bit。
